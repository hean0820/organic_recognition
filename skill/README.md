# reusable_pynq_validation

本技能包包含两个可独立使用的校验脚本。它们不导入 PYNQ、不访问 MMIO、不下载 bitstream；板卡及题目信息通过 profile 或输入数组提供。目录内不包含与本队未验证能力有关的第三方 Skill 集合。

## 1. Overlay 文件与 HWH 接口检查

脚本：`scripts/validate_overlay.py`。依赖 Python 3，使用标准库。适用于能提供 bit/HWH 配对文件、已知 SHA256 和预期 IP 基地址的 PYNQ 工程，可用于另一题目或板卡的提交前静态检查。

在仓库根目录运行本项目例子：

```bash
python -B skill/scripts/validate_overlay.py --profile skill/profiles/current.json --root src/ps/psv7_pynq
```

复用到其他题目时，按以下结构创建自己的 profile，路径相对于 `--root`，SHA256 和地址必须来自该题目已确认的产物与接口设计：

```json
{
  "name": "my_board_task",
  "files": {
    "bit": {"path": "overlay/design.bit", "sha256": "replace_with_64_hex_digits"},
    "hwh": {"path": "overlay/design.hwh", "sha256": "replace_with_64_hex_digits"}
  },
  "ips": {"my_accel_0": "0x43c00000"}
}
```

脚本检查文件存在、路径未超出根目录、两个文件哈希和每个指定实例的 HWH MEMRANGE 地址；缺失或歧义会失败。成功返回 `passed=true`，错误返回失败退出码。其他题目可只复制此脚本和自建 profile，不需要有机物数据、模型或原板卡。

### 1.1 从哪些失败或观察中总结

工程多次迭代后，不同版本可能保留相近的文件名和相同的 IP 实例名，但硬件内容或地址布局已经变化。由此得到的观察是：仅凭文件名、所在文件夹或“文件能够打开”，不能确认它就是准备交付的硬件版本，也不能确认软件所用地址与 HWH 一致。这是文件身份和接口一致性方面的风险观察，不将其写成缺少日志支持的具体板端故障。

把这个观察转化为检查需求时，需要回答两个不同的问题：第一，收到的 bit 和 HWH 是否分别等于团队已确认的那一份文件；第二，HWH 中指定 IP 的地址是否等于软件预期地址。前者用 SHA-256 核对，后者读取 HWH 元数据核对。只检查哈希不能发现配置中预期地址写错，只检查地址也不能确认 bit 文件版本，因此保留两类检查。

### 1.2 如何提炼成可复用工具

提炼时先区分“每个工程都需要的检查逻辑”和“只有当前题目才知道的参数”。文件存在性、目录范围、SHA-256 计算和 HWH 地址解析保留在 `scripts/validate_overlay.py` 中；bit/HWH 路径、期望哈希、IP 实例名和地址放入 `profiles/current.json`。

执行时，工具先检查文件位置与身份，再读取 HWH 的 `MEMRANGE` 节点，按 `INSTANCE` 汇总 `BASEVALUE`。每个配置中指定的实例必须对应唯一的预期地址，否则返回失败。配置未列出的其他 IP 不属于本次核对范围。

这种拆分使下一支队伍可以复用同一脚本，仅替换自己的配置，不需要保留有机物类别、模型参数或本板卡地址。配置必须由该队伍依据已确认的硬件产物和接口设计建立，不能从一组来源不明的文件生成哈希后，就据此宣布它们配套正确。

### 1.3 如何验证有效

验证采用“正常样例能够通过，单项错误能够被检出”的方法。已有结果保存在 [organization_verification.json](../sim/results/organization_verification.json)，记录日期为 2026-10-23：

1. **正常文件和地址。**使用当前工程配置检查 bit/HWH 及 6 个 IP 地址，记录 `skill_profile_positive.passed = true`、`ip_count = 6`，确认脚本能接受当前已知配置。
2. **错误哈希。**改变配置中的 bit 期望哈希，记录 `skill_bad_hash.rejected = true`，错误信息为 `File hash differs: bit`，确认文件身份不符能够被检出。
3. **错误地址。**将配置中的 CNN 预期地址偏移 4 字节，记录 `skill_bad_address.rejected = true`，错误信息为 `Missing or ambiguous HWH address: cnn_ps_if_0`，确认地址不符能够被检出。

反例只改变一个检查条件，目的是区分工具究竟发现了什么问题；这些错误是验证时主动构造的，不是历史上板故障记录。对反例而言，“被拒绝”才是符合预期的结果。

其他队伍复验时，可先运行前述正常命令，再复制一份 profile，分别修改期望哈希和一个 IP 地址后重新运行。正常样例应退出为 0；两种错误样例应退出为 1，并分别报告文件哈希或地址错误。不要直接修改正式交付配置来保存反例。

### 1.4 边界如何确定

边界由工具实际读取的信息、配置前提和现有测试覆盖共同确定：

- **配置前提：**脚本把 profile 当作判定依据，无法自动发现它是否正确。错误文件与错误配置相互吻合时仍可能通过，因此配套关系需先由构建来源和人工审查确认；更新硬件后也需重新审查配置。
- **静态检查边界：**脚本只读取文件，不访问开发板。通过只能说明这些文件与指定配置一致，不能证明当前 PL 已加载该 bit，也不能证明时钟、引脚、时序、DMA 或系统功能正确。
- **接口检查边界：**目前仅解析 HWH 的 `MEMRANGE/INSTANCE/BASEVALUE` 并检查指定实例的基地址，不检查完整寄存器语义、数据位宽或协议行为。HWH 结构变化时，应先适配解析逻辑并重新验证。
- **验证覆盖边界：**现有归档明确支持正常配置、错误哈希和错误地址三项结论。路径越界等其他代码分支不能仅因代码存在，就写成已经完成专项验证；也没有第二块实体板或另一题目的上板验证结论。

因此，该技能用于上板前的文件和接口静态核对。通过后仍需执行实际加载、驱动身份检查和功能验收，不能用它替代整机测试。

## 2. NPY/NPZ 整数参考逐值比对

脚本：`scripts/compare_arrays.py`。依赖 Python 3 和 NumPy。适用于确定性整数或定点输出、固定输入回归、软件/RTL Golden 比较。

```bash
python -B skill/scripts/compare_arrays.py /path/to/expected.npy /path/to/actual.npy
```

也可传入两个 NPZ。NPZ 的键集合、对应数组的形状、dtype 和每个元素均需一致；脚本不做隐式广播或类型转换。成功退出码为 0；值、结构、类型不同或文件错误时返回失败退出码，并输出 JSON。

### 2.1 从哪些失败或观察中总结

定点 CNN 从软件迁移到 RTL、再进行并行优化时，目标是保持同一输入下的整数计算结果。仅比较最终类别会遗漏一类问题：即使部分分值已经变化，只要最大值所在位置不变，分类结果仍可能相同。因此，“类别相同”不足以证明部署数值一致。

另一个观察是，数组的形状和类型也是接口约定的一部分。相同的数字若使用了不同位宽、有符号性或排列方式，其存储及后续运算含义可能不同；自动转换类型、自动广播或重排后再比较，会掩盖本应暴露的接口差异。

据此提炼出的检查目标是：在参考数据和实际数据已经导出的前提下，逐项核对键、形状、类型与元素值。该来源属于从项目数值验收需求中得到的方法总结，不将所有可能的数值问题都写成已实际发生的故障。

### 2.2 如何提炼成可复用工具

将“读取数据并严格比较”的逻辑独立为 `scripts/compare_arrays.py`，由调用者传入参考文件和实际文件，不在脚本中写死 22 类、64×64 输入或任何 CNN 层名。

对于 NPY，脚本把整个数组作为一个比较对象；对于 NPZ，先要求键集合相同，再逐键检查数组形状和 dtype，最后统计不相等的元素数。脚本不会自动转换类型、广播、转置或调整维度。只要有一个元素不同，就返回 `passed = false`；结构或类型不符则报告错误。

这种形式可以复用到其他确定性整数算法的输出、RTL 仿真导出张量或固定输入回归。导出数据、产生黄金参考以及运行硬件仍由各工程自己的工具完成，本脚本只负责已保存数组的比较。

### 2.3 如何验证有效

验证从冻结 Golden 的 INT32 logits 构造样例，结果同样保存在 [organization_verification.json](../sim/results/organization_verification.json)：

1. **完全一致的数组。**保存相同参考与实际数组，记录 `skill_equal_arrays.passed = true`，`differences.array = 0`，确认正常输入可以通过。
2. **单个数值错误。**保持形状和类型不变，只改变一个元素，记录 `skill_changed_element.passed = false`，`differences.array = 1`。这既证明能够发现错误，也核对了差异计数，而不是仅检查程序是否报错。
3. **数据类型错误。**将 INT32 改为 INT64，记录 `skill_wrong_dtype.rejected = true`，错误信息为 `Shape or dtype differs: array`，确认工具不会通过隐式类型转换掩盖接口差异。

复验时先保存一份参考数组及其相同副本，再分别制作“只改一个元素”和“只改 dtype”的副本，使用前述命令逐一比较。预期退出码依次为 0、1、1。修改单个元素时应避免溢出后仍等于原值，确保反例确实发生变化。

这些结果证明的是比较工具对所测错误的检出能力。样例来自参考数据及其人工修改副本，不代表重新运行了 FPGA，也不能计入 132 组板端测试。

### 2.4 边界如何确定

- **数值规则边界：**工具采用逐元素精确相等，不提供浮点容差、量化尺度换算或自动布局转换。需要容差的算法应另行定义并验证规则，不能把本工具的失败直接判成算法错误。
- **参考可信性边界：**脚本能够判断两个文件是否一致，但不能判断参考是否正确，也不能确认实际文件由哪块板或哪个版本产生。使用者仍需保存输入、参数版本、运行来源和参考生成方式；相同的错误数据也可能比较通过。
- **格式边界：**支持 NPY/NPZ，加载时禁用 pickle，不适用于需要反序列化 Python 对象的 object 数组。数组元素可以比较不代表工具理解其物理单位或通道语义。
- **验证覆盖边界：**现有归档明确记录了相同数组、单元素差异和 dtype 差异。NPZ 键集合、形状差异等虽有检查逻辑，但该记录未逐项给出专项测试结果，不能据此声称已覆盖全部格式和错误组合。
- **结论边界：**所测数组一致只支持这些输入上的数值一致性，不代表所有输入均正确，更不能替代独立数据集上的识别准确率评估。

因此，该技能作为部署一致性检查的一环使用。应先冻结输入和参考生成规则，再保存待测输出并比较；不能仅凭比较结果外推模型泛化能力或整机功能。

## 3. 从观察到验证的过程

以上两项技能按以下步骤从项目经验中整理。这里说明的是工程方法的提炼顺序；不补写未经保存的逐字提示词，也不把人工构造的反例描述为真实上板事故。

1. **记录具体观察。**分别记录“文件名称不能证明硬件版本及接口一致”和“分类相同不能证明整数输出一致”。将问题写成可以检查的条件，避免停留在“注意版本”“加强验证”等笼统提醒。
2. **确定判定依据。**前者以已确认文件的哈希及预期地址为依据；后者以冻结参考数组及其形状、类型和值为依据。先确认依据来源，再执行检查，避免用待检查对象自己定义正确答案。
3. **分离通用逻辑和题目配置。**把地址、文件路径及哈希放入 profile，把待比较数组作为参数传入；保留独立脚本，使其他题目无需复制本项目业务代码即可使用。
4. **建立正常样例。**先确认当前正确配置和相同数组能够通过，避免把“所有输入都拒绝”的脚本误认为有效工具。
5. **构造单因素反例。**分别改变哈希、地址、一个数值及 dtype，保持其他条件不变，检查拒绝结果及错误信息是否对应预期。对数值反例同时核对差异计数。
6. **保存验证证据。**将结果写入 `sim/results/organization_verification.json`，保留正常和反例的独立字段。该记录标注 `hardware_accessed = false`、`new_vivado_run = false`，明确属于离线工具验证。
7. **据证据确定边界。**把检查不到的信息、必须信任的外部依据、未专项测试的分支和未验证的平台逐项列明。可配置接口说明具备复用条件，不等于已经在所有板卡上验证。
8. **说明迁移与复验方法。**使用者替换自己的配置或参考数据后，先重做正常样例与单因素反例；改变 HWH 格式、数值规则或文件格式时，需要适配并补充验证。验证通过后，再进入其工程的上板或系统验收。
